# Candidate-Family Execution Spine Roadmap

**Goal:** Extract the domain-neutral execution machinery discovered in the RSA/NDim reducer programme into reusable Core owners without importing RSA/GF(2)/CUDA semantics or forcing unrelated lanes into requirement/conflict structure they do not own.

## Canonical hierarchy

```text
CandidateFamilyExecutionExact
  family admissibility
  + compose
  + independent global-admissibility payment

        ^ specialization
        |
RequirementConflictBatchExecutionExact
  conflict / coRequirement / independent vocabulary
  + requirement closure
  + conflict freedom
  + independent global-validity payment
```

The stronger batch spine projects canonically to the weaker candidate-family spine.

Relation knowledge is open-world: `conflict / coRequirement / independent` is a reusable vocabulary, but domains are not required to expose a total candidate-pair classifier. Absence of a relation receipt is not independence.

## Migration admission tests

A lane may instantiate `CandidateFamilyExecutionExact` only if it has:

1. an explicit selected-family carrier;
2. a proof-valued family-admissibility predicate;
3. an explicit composition map;
4. a proof-valued global-admissibility predicate independent of family admissibility.

A lane may instantiate `RequirementConflictBatchExecutionExact` only if it additionally has:

1. explicit conflict and co-requirement semantics, or typed relation receipts;
2. a requirement-closure predicate;
3. a conflict-freedom predicate;
4. no assumption that either predicate implies the other;
5. global validity checked after selection/closure.

A lane may claim an added observational coordinate is paying only when an explicit downstream witness exists, preferably `CoordinateSeparatesCollision` / `ProjectionCollision` or a declared consumer-improvement theorem. Merely adding NDim axes is not payment.
